# TU102 Windows unlock and SM75 research

Research snapshot: 2026-10-28. **There is no demonstrated Windows unlock in the supplied projects.** The Linux project reports its own results on a Dell RTX 2080 Ti 22GB (`10de:1e07`) with driver 575.51.03; these are upstream claims, not reproduced here, and not evidence that the Windows driver retains the effect. Real Windows compilation, kernel execution, inference, boot unlock and post-driver MMA remain unverified. Source, binaries, machine, driver and full model must be bound to each run.

## Hardware sequence and acceptance

First collect actual Windows 11 native hardware inventory, GPU PCI/subsystem and VBIOS, motherboard/firmware, driver/toolkit, physical memory and 22 GiB-class reported VRAM, power/cooling and recovery details. Preserve independent original boot selection and tested recovery before firmware experiments. Progress from bounded host tests, to read-only EFI enumeration, to a no-unlock boot handoff, then only a reviewed profile-specific implementation with explicit DMA ownership, quiescence, reset and failure containment. Unknown profiles remain unsupported. Test with the stock Windows driver loaded after boot: paired locked/unlocked MMA results on the same device, driver, benchmark and numerical inputs must include correctness, measured times, power/clocks and repeated trials. A pre-driver result alone is insufficient; neither host tests nor a successful boot show that unlock persisted.

Before optimization, run actual SM75 kernel numerical oracles and a same-GGUF reference comparison, then the G1 32K input plus output and the G2–G7 requirements in the roadmap. Preserve the same binary/model fingerprints for matched comparisons, record controlled settings, actual token counts, memory and full raw outputs. Report failed and unrun cases, regressions and variance. Tensor Core throughput is not end-to-end inference speedup; GEMV, memory transfers, routing, CPU work and context length may dominate.

Windows WDDM's [TDR overview](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/timeout-detection-and-recovery) describes GPU timeout recovery; [TDR registry guidance](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/tdr-registry-keys) says those keys are for targeted driver development and debugging, not end-user applications to manipulate. Design benchmark work to complete within normal limits, capture timeout/device-reset failures, and do not present changing TDR as a qualification step.

## Evidence validator

`python tools/check_acceptance.py manifest.json` checks local files and prints JSON. Gate statuses use `not_run`, `failed`, or submitted `passed`; all seven must be present. An all-not-run manifest needs only `schema_version: 1` and `gates` with objects such as `{"status":"not_run"}`. `config/unlock-capabilities.json` records current capability status separately, not a completed evidence manifest.

For any submitted pass, add `inventory` with `os: "Windows 11"`, `native: true`, `gpu: "TU102"`, `compute_capability: "7.5"`, integer `vram_bytes` (21–23 GiB), and `raw`; `source` with the full 40-hex project `commit`, separate full 40-hex `strata_commit` matching `strata.commit` in its `lock`, and a nonempty `patches` list of hashed integration patch artifacts; `binary`, `model`, and `build_record`. Each artifact is `{"path":"relative-or-absolute-path", "sha256":"lowercase-64-hex"}` and is read and hashed; model must match this repository's published model lock. Each submitted passed gate needs `environment: "native_windows_hardware"`, matching `binary_sha256` and `model_sha256`, and a nonempty `artifacts` array. G5/G6 also need a hashed `post_driver_mma.benchmark` artifact and `post_driver_mma.locked` and `.unlocked` runs. Each run must specify the hardware environment, the benchmark artifact's SHA as `binary_sha256`, matching nonempty `device_id`, `driver_version`, `test_id`, `shape` and `dtype`, and separate hashed `raw_result` artifacts. The benchmark can be a different executable from the inference engine and a pure MMA test needs no model. G6's end-to-end gate record still requires the inference binary and model hashes. Use actual full files; relative paths resolve against the manifest directory.

For example, the `source` portion of a submitted-pass manifest has this shape (replace placeholders with actual files and hashes):

```json
{
  "commit": "<40-hex-project-commit>",
  "strata_commit": "<40-hex-upstream-commit>",
  "lock": {"path": "sources.lock.json", "sha256": "<64-hex-file-hash>"},
  "patches": [{"path": "0001-integration.patch", "sha256": "<64-hex-file-hash>"}]
}
```

This is a consistency and file-integrity check, not an attestation system. The project commit is a supplied identifier, and the checker does not prove that the patch list is complete or that patches were applied to that commit. Raw inventory and build records are not authenticated, contents are not interpreted to prove a device, successful boot, numerical correctness, timing, recovery or build provenance; labels and hashes can be fabricated. Even structurally complete evidence is `candidate_evidence_requires_review`, with `hardware_unlocked: false`, never automatic acceptance. Independent review must inspect underlying records against each roadmap gate, and reject synthetic, incomplete, mismatched or misleading results. For failed gates retain their raw logs separately; this validator does not certify failures or convert them into passes.
